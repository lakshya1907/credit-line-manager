# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Adaptive credit line manager built on the UCI "Default of Credit Card Clients" dataset (`data/raw/uci_credit.csv`). It predicts default probability (PD) and exposure (EAD), simulates alternative credit limits per customer, picks the limit that maximizes risk-adjusted expected profit, then applies portfolio-level budget constraints and stress tests.

## Commands

```bash
pip install -r requirements-dev.txt      # includes requirements.txt + pytest; venv/ is gitignored
python run_all.py                        # full pipeline (run from repo root)
python run_all.py --data path/to/file.csv
python run_analytics.py                  # segments + backtest + policy comparison; needs run_all.py's models/*.pkl first
pytest                                   # tests/*.py, pure-function unit tests only (no model training)
pytest tests/test_portfolio_opt.py -q    # single file

createdb credit_line_manager             # one-time, needs local Postgres running
cp .env.example .env                     # adjust DATABASE_URL if your local Postgres differs
alembic upgrade head                     # applies src/db/models.py's schema
python sync_run_to_db.py                 # loads the latest run_all.py/run_analytics.py run into Postgres
python sync_run_to_db.py --all           # loads every archived run

uvicorn src.api.app:app --reload         # API; needs DATABASE_URL reachable + models/*.pkl to be fully useful
                                          # (starts and reports degraded readiness without either)

cd frontend && npm install && npm run dev    # frontend; proxies /api/* to localhost:8000, see frontend/README.md

docker-compose up --build                 # postgres + api + frontend; use `docker-compose`, not `docker compose`
                                           # (the plugin isn't on this machine's PATH -- see CLAUDE.md's
                                           # Infrastructure section); do not run alongside the local dev
                                           # servers above, they'll fight over ports 8000/5432/3000
docker-compose exec api python run_all.py         # first time only: seed the containerized Postgres
docker-compose exec api python sync_run_to_db.py
```

There is no linter or build step (Python side; the frontend has `tsc -b` as part of `npm run build`). Run everything from the repo root — `run_all.py` imports `src.*` as a package and all paths (`data/processed`, `models`, `reports`) are relative to the cwd.

The `tests/` suite covers the pure-function modules (`economics.py`, `calibrate.py`, `counterfactual.py`, `portfolio_opt.py`, `decision_engine.py` with fake PD/EAD models) — it does not train real models or run the pipeline end-to-end. `pyproject.toml` sets `pythonpath = ["."]` so `from src... import ...` resolves without installing the package.

The full pipeline (fresh model training included) runs in ~10s. `decision_engine.recommend_limits` scores every customer's baseline and every (customer, candidate-limit) pair via `counterfactual.build_counterfactual_batch` in a small constant number of batched `pd_model`/`ead_model` calls (2 and 1 respectively, regardless of `n`), not one call per row/candidate — the per-call overhead of ~210,000 individual 1-row model calls, not the actual model compute, was what made this slow before (~10 min for one run, ~27 min for a 4-shock stress test). See `git log` on `decision_engine.py`/`counterfactual.py`/`economics.py` for the change and `tests/test_counterfactual.py`'s equivalence tests against the old per-row path. SHAP is capped at `sample_n=5000` in `step_explainability`.

## Pipeline architecture (`run_all.py`)

Steps run in this order (note explainability runs before portfolio, despite its "6b" label):

1. `data_prep` — load CSV, rename target (`default.payment.next.month` → `TARGET`), clip negatives.
2. `features.build_features` — utilization, payment-ratio, delinquency, bill-trend and interaction features; renames `ID` → `customer_id`. Writes `data/processed/features.parquet`.
3. `pd_model` (XGBClassifier) + `calibrate` (isotonic on the validation split). A calibrator is a `(kind, obj)` tuple — always apply it via `apply_calibrator`, never call `.predict` on it directly.
4. `ead_model` (XGBRegressor) — target is a balance proxy `0.7*BILL_AMT1 + 0.3*BILL_AMT2`.
5. `decision_engine.recommend_limits` — for every customer and every `LIMIT_MULTIPLIERS` candidate at once (see the "Vectorized" note above): rebuild limit-dependent features (`counterfactual.build_counterfactual_batch`), re-score PD, scale balance by a log-elasticity (`economics.balance_under_limit`), compute EP. Increases are blocked by PD guardrails (`PD_INCREASE_MAX`, `PD_DECREASE_MIN`). Takes optional `pd_shock`/`ead_shock` (proportional, applied before the guardrails/EP comparison, clipped to valid ranges) so stress scenarios can change which action is chosen, not just its reported numbers. Writes `recommendations_raw.csv`.
6. `explainability.run_explainability` — SHAP top features + human-readable reason codes (`_REASON_MAP`, matched by feature-name substring); overwrites `recommendations_raw.csv` with the annotated version and writes `audit_log.csv` and `reports/shap_global_importance.csv`. `build_explainer` always uses `feature_perturbation="tree_path_dependent"` — `"interventional"` unconditionally raises on any XGBoost model with `enable_categorical=True` (the default since XGBoost 2.x, unrelated to whether any column is actually categorical).
7. `portfolio_opt.portfolio_select` — greedy selection of increases by ROI (`ep_uplift / el_uplift_proxy`) under `EL_BUDGET` / `EAD_BUDGET`; unapproved increases revert to hold. Decreases/holds always pass. The running `used_el`/`used_ead` accumulate the *signed* `el_uplift_proxy`/`ead_uplift` — do not clamp to `max(..., 0.0)` before accumulating, or negative-delta rows silently stop contributing to the budget check (this was a real bug; see `git log` on this file). When an increase is rejected, **every** "recommended" column (`recommended_limit`, `pd_recommended`, `ead_recommended`, `ep_recommended`, `ep_uplift`, `el_uplift_proxy`, `ead_uplift`) must revert to its "current"/zero value, not just `action`/`recommended_limit` — otherwise a row labeled `"hold"` still reports the profit/risk of the increase that was never approved, silently inflating `total_ep_uplift` (this was also a real bug, found via the policy-comparison analytics in `run_analytics.py`; see `reports/analytics_findings.md` §1 and `git log` on this file). Writes `recommendations_final.csv`.
8. `stress_test.py` — see its module docstring for the two stress-testing paths and when each is used: `run_stress_scenario` (genuine re-simulation via `recommend_limits(pd_shock=...)`, used by `run_all.py` step 7/`step_stress_test`) vs. `apply_pd_shock`/`apply_ead_shock` (fast O(1) rescaling of an already-decided recommendation table; cannot change which action was chosen — not currently called by anything since the Streamlit dashboard that used it was removed, kept for a possible future live-comparison endpoint). `step_write_report` writes `reports/pipeline_metrics.txt`.
9. `archive_run` — copies this run's output files into `data/processed/runs/<run_id>/`, writes `run_manifest.json` (config snapshot + every metric for that run — self-contained, doesn't depend on whatever the flat "latest" files happen to contain later), and appends one row to `data/processed/runs_index.csv`. See "Run history" below.

### Run history

Every `run_all.py` run gets a `run_id` (`_new_run_id`: UTC timestamp + a short random suffix, so runs sort chronologically and never collide). The top-level flat files (`data/processed/recommendations_raw.csv`, `reports/pipeline_metrics.txt`, etc.) are still overwritten each run — that's deliberate, matching the pattern the (now-removed) Streamlit dashboard used, "the current plan" as a single always-latest artifact — but `archive_run` (the last step of `main()`) additionally:
- copies that run's output files into `data/processed/runs/<run_id>/`
- writes `data/processed/runs/<run_id>/run_manifest.json`: `run_id`, start/finish timestamps, wall time, git commit, the raw data path, a full config snapshot (budgets, guardrails, multipliers, APR/LGD grid, elasticity, seed — the policy that produced this run's recommendations, not just the recommendations themselves), PD/EAD model metrics, the portfolio summary, and the stress-test results
- appends one flattened summary row to `data/processed/runs_index.csv` (creating it with a header on the first run) — this is the file to read for any "how has X trended across runs" analysis; don't recompute that by scanning `runs/*/run_manifest.json`

Both `runs/` and `runs_index.csv` live under `data/processed/`, so they're gitignored like everything else there — this is deliberately plain per-run files (`archive_run` in `run_all.py`), not a database. Before this, every run overwrote its own history (including the file literally named `audit_log.csv`), so there was no way to compare runs or see how a config change affected the portfolio over time; this is the fix, and the natural precursor to a future `model_runs`/`portfolio_runs` schema if/when this becomes a real database.

### Key cross-file invariants

- **Customer ID handling**: `customer_id` stays in `X` but every model call drops it first (the `id_col` / `trainable()` pattern repeated in `pd_model`, `ead_model`, `decision_engine`, `run_all`). Models are trained on the column set without it, so column order/names must match exactly.
- **Counterfactual features must mirror `build_features`**: any new feature derived from `LIMIT_BAL` (utilization and interactions) must be added to `counterfactual._recompute_util_features` — the single core implementation shared by `apply_new_limit_features` (single-row Series in/out, e.g. for a future single-customer what-if endpoint) and `build_counterfactual_batch` (the vectorized `(customer x candidate)` grid decision_engine.py actually uses). `util_cols` there is built explicitly from `util_1..util_6` — do not switch it to `c.startswith("util_")`/`.startswith("util_")`-style matching against existing columns, since the frame still holds the *old* aggregate columns (`util_mean`, `util_max`, `util_std`, `util_last`, `util_trend`, `util_x_delinq`) at that point, which also match that prefix and would contaminate the recompute (this was a real bug; see `git log` on this file and `tests/test_counterfactual.py`, including its `apply_new_limit_features`-vs-`build_counterfactual_batch` equivalence test).
- **Economics** (`economics.py`): EP per scenario = `(APR/12)·EAD − PD·EAD·LGD` over the APR × LGD grid in `config.py`; `ROBUST_MODE="worst_case"` takes the min across scenarios. Given the default grid, worst-case EP-per-dollar-of-EAD is only positive for PD below ~0.019 — above that, minimizing EAD (i.e. decreasing the limit) is the economically rational choice even before any PD guardrail kicks in.
- **All tunables live in `src/config.py`** (limit multipliers, APR/LGD scenarios, elasticity, budgets, guardrails, seed).
- **The counterfactual PD is a correlation, not a causal estimate**: raising a customer's limit lowers their utilization ratio, and the PD model reads low utilization as materially lower risk (since that's the correlation in the training data) — so counterfactual PD tends to drop sharply whenever a limit is raised. In practice this means `EL_BUDGET` essentially never binds (aggregate `el_uplift_proxy` across approved increases comes out net negative). This is a modeling limitation to be aware of, not something `portfolio_opt.py`'s accounting can fix.

## Frontend (`frontend/`)

React + TypeScript + Vite SPA, not Next.js — this is an internal analytics/ops tool with no SEO/SSR need, so Next.js's actual value props don't apply here; a client-side-rendered SPA hitting a REST API is the simpler, better-fitting choice (see the roadmap discussion this was planned against, referenced in git history). Replaces the former Streamlit dashboard (`src/dashboard_app.py`, removed — it was explicitly a prototype/reference UI, not meant to be the production frontend), reading from `src/api/` instead of flat files directly.

- **Pages**: `RunsPage` (history + trigger-and-poll a new run), `RunDetailPage` (portfolio summary + a **read-only** policy comparison table — pre-computed named scenarios from `policy_compare.py`, not a live slider; see below for why — + stress test/segment/fairness/backtest charts), `ActionQueuePage` (filterable/paginated recommendations, TanStack Table), `CustomerDrilldownPage` (cross-run history + live what-if scoring via `POST /customers/{id}/score`). Deliberately does not reimplement "Model Diagnostics" — that was an internal model-debugging view, lower value than the other four pages, per the roadmap's scoping call.
- **Why the Policy Simulator is read-only here, not a live slider like Streamlit's was**: a live portfolio-level policy slider needs a synchronous full-portfolio re-run per drag; Streamlit's version used the fast O(1) rescaling approximation (`apply_pd_shock`/`apply_ead_shock`) for that. Rather than either reimplementing that approximation in the frontend or adding a new live-comparison API endpoint, this shows the actual pre-computed named-policy comparisons already produced by `run_analytics.py`'s `policy_compare.py` and synced to `portfolio_runs` — real numbers, not an approximation, at the cost of not being adjustable in real time. A live version would be a legitimate future API addition, not a frontend-only change.
- **`frontend/src/api/types.ts`** mirrors `src/api/schemas.py` by hand. If this API grows much further, generate these from FastAPI's OpenAPI schema (`openapi-typescript` or similar) instead of hand-maintaining two copies of the same contract — not done yet since the surface is still small enough that drift is easy to catch, but don't let that scope creep without revisiting this.
- **CORS**: `src/api/app.py` reads `CORS_ORIGINS` (comma-separated) from the environment, defaulting to Vite's own dev-server origin as a convenience. Local `npm run dev` doesn't actually need this — it goes through `vite.config.ts`'s dev proxy — but a production build calling the API directly does.

## Analytics (`run_analytics.py`, `src/analytics/`)

Reads `models/*.pkl` (from `run_all.py`) and produces, to `data/processed/analytics/` (gitignored) plus stdout:
- **`segments.py`** — buckets customers into behavioral segments (`util_tier`, `delinquency_tier`) and demographic segments (`sex_segment`, `education_segment`, `marriage_segment`, `age_segment`) via `add_segment_columns`, then `segment_summary` aggregates a recommendation table per segment value. `SEX`/`EDUCATION`/`MARRIAGE` are fed to `pd_model` as raw numeric features (`build_features` passes them through unchanged) — a real fair-lending concern (ECOA, in the US) independent of whether they're "intentional" — so `disparate_approval_ratio` (a four-fifths-rule-style check) exists specifically to make that checkable, not just to slice data for its own sake. See `reports/analytics_findings.md` §2.
- **`backtest.py`** — see its module docstring for why a classic time-based train/test split doesn't apply to this dataset (one cross-sectional snapshot per customer, not repeated observations over time). `restricted_feature_backtest` instead compares PD model performance trained on only the N most recent months of behavior (via a small, deliberately consistent feature set, `build_restricted_features` — not `features.build_features`, so absolute metrics aren't comparable to the production model). See `reports/analytics_findings.md` §3 for the "recency matters more than history length" finding.
- **`policy_compare.py`** — re-runs the decision engine + portfolio selection under several named guardrail/budget overrides via `decision_engine.recommend_limits`'s `pd_increase_max`/`pd_decrease_min` parameters (added for this; default `None` falls back to `src.config`) and `portfolio_select`'s existing `el_budget`/`ead_budget` params. Only practical because of the vectorization in the perf commit — each policy is a full ~30k-customer run, ~0.3s. See `reports/analytics_findings.md` §4 for the "more approvals ≠ more profit" finding.

`reports/analytics_findings.md` is the actual write-up (git-tracked); `data/processed/analytics/*.csv` is the regeneratable evidence behind it.

## Database (`src/db/`, `alembic/`, `sync_run_to_db.py`)

Every table mirrors a file artifact that already exists (see `src/db/models.py`'s module docstring for the full mapping) — this is a migration target for `data/processed/runs/<run_id>/`, not a speculative schema, and it fixes a real gap: `run_all.py` overwrites its top-level flat files on every run (deliberately — see "Run history" below and the archival design), so before this there was no way to query or compare across runs. `sync_run_to_db.py` writes to it; `src/api/` (below) is what reads from it.

- **`src/db/models.py`** — SQLAlchemy 2.x declarative models: `ModelRun` (one row per `run_all.py` execution, config snapshot + PD/EAD metrics) → `PortfolioRun` (one-to-many; one row per `portfolio_select()` outcome — usually one "default" row from `run_all.py` itself, plus one row per named scenario if `run_analytics.py`'s `policy_compare.py` was run against that model_run), `Recommendation` (one row per customer, the engine's raw pre-portfolio-budget output — this is what `recommendations_raw.csv`/`audit_log.csv` hold today, minus their per-row-repeated run-level metadata which now lives on `ModelRun`/`PortfolioRun` instead), `StressTestResult`, `SegmentMetric`, `BacktestResult`, `FairnessCheck`.
- **`src/db/session.py`** — reads `DATABASE_URL` from the environment or a local `.env` (see `.env.example`, gitignored); defaults to `postgresql+psycopg2://localhost:5432/credit_line_manager`.
- **`alembic/`** — schema migrations. The initial migration (`alembic/versions/0001_initial_schema.py`) was autogenerated against a real local Postgres then reviewed by hand, not trusted blindly — and both `alembic upgrade head` and `alembic downgrade base` were verified to actually apply/reverse cleanly against that Postgres instance (not just SQLite). Future schema changes: edit `src/db/models.py`, then `alembic revision --autogenerate -m "..."`, then review the generated file before committing it — autogenerate is a draft, not a migration.
- **`sync_run_to_db.py`** — the actual data migration: reads a run's `run_manifest.json` (+ `recommendations_raw.csv`, `stress_test_results` from the manifest, and `analytics/*.csv` if `run_analytics.py` was run for that run_id) and upserts it into Postgres. Idempotent per `run_id` (re-syncing deletes and replaces via `ModelRun`'s cascade delete, rather than erroring or duplicating). `--all` syncs every archived run; default syncs just the latest.
- **A real bug found building this, worth knowing about**: psycopg2 doesn't reliably adapt numpy scalar types (`np.float64`/`np.int64`) that pandas hands back from `DataFrame.iterrows()`/column access even on a DataFrame that "looks like" plain floats — it surfaced as `psycopg2.errors.InvalidSchemaName: schema "np" does not exist` on an INSERT, because SQLAlchemy's batch-insert path ended up stringifying an `np.float64` repr into the query text. Fixed via `sync_run_to_db._native()`, applied to every DataFrame-sourced value before it reaches an ORM object — don't remove that cast when adding new sync logic.

## API (`src/api/`)

Endpoints are need-driven, not generic CRUD over every table — each one answers a question the file-based pipeline couldn't (see the roadmap discussion this was planned against). `src/api/app.py`'s `lifespan` loads `models/*.pkl` + rebuilds the feature matrix **once** at startup into `app.state.ml`, not per-request; if those files don't exist yet (fresh clone), the app still starts, `GET /readiness` reports `models_loaded: false`, and `/customers/*/score` returns 503 rather than crashing at import time.

- `GET /health` — liveness only. `GET /readiness` — DB reachable + models loaded; a load balancer should use this one, not `/health`.
- `GET /runs`, `GET /runs/{run_id}` (nested `portfolio_runs`/`stress_test_results`/`segment_metrics`/`backtest_results`/`fairness_checks`) — read from Postgres via `src/db/models.py`.
- `GET /runs/{run_id}/recommendations?action=&customer_id=&limit=&offset=` — filtered/paginated; exactly the query shape that was awkward against a flat CSV (`ix_recommendations_action` on the model exists for this).
- `POST /runs` — triggers a full `python run_all.py` pipeline run as a background job (via `BackgroundTasks`, see `src/api/jobs.py`), then syncs the result into Postgres so it's immediately queryable — returns `202` + a `job_id` to poll at `GET /runs/jobs/{job_id}`. **`src/api/jobs.py`'s job registry is an in-memory dict, deliberately not a persisted queue** — the right scope for a single-instance deployment, but it means job status is lost on restart and would break under multiple uvicorn workers (each has its own dict); read that module's docstring before assuming this survives a restart or scales to multiple workers.
- `GET /customers/{customer_id}/history` — a customer's recommendation across every synced run, oldest first. This is the concrete thing the pre-#2/#4 file-based pipeline structurally could not answer (every run overwrote the last one's output), not just a convenience wrapper.
- `POST /customers/{customer_id}/score` — live single-customer what-if scoring against the **in-memory** models (not the DB): with no body, runs the same best-candidate search `decision_engine.recommend_limits` does, for just this one customer (~7 model calls); with `{"new_limit": X}`, scores that exact hypothetical limit and reports `guardrail_blocked` — reuses `counterfactual.apply_new_limit_features`/`economics.py`/`PD_INCREASE_MAX`/`PD_DECREASE_MIN` directly rather than reimplementing the guardrail logic.
- **`src/api/auth.py`** — optional `X-API-Key` header check via `require_api_key`, applied only to the two mutating endpoints (`POST /runs`, `POST /customers/{id}/score`). A no-op unless the `API_KEY` env var is set — disabled by default so local dev and the frontend (which doesn't send this header) keep working without extra setup. This is a shared-secret header, not a real auth system (no accounts/sessions/roles) — the right-sized mechanism for an internal tool with no user-facing login, not an under-built one; see the module docstring.
- **`src/api/logging_config.py`** — JSON-lines structured logging (one log record per line, parseable by any container log collector without a separate shipping agent), wired in via a request-logging middleware in `app.py`. `configure_logging()` is called from inside `lifespan`, not at module import time — uvicorn applies its own `logging.config.dictConfig()` (`disable_existing_loggers=True`) when it starts the server, *after* this module is imported, which silently discarded every log line when this was called at import time instead (found by actually reading `docker logs` and seeing uvicorn's plain-text access lines instead of JSON, not by reading the code). `lifespan` startup runs after uvicorn's own logging setup, so that's the reliable place.

**Verified end-to-end for real, not just via automated tests**: ran `python run_all.py` three times, `python run_analytics.py` once, `python sync_run_to_db.py --all`, then drove every endpoint above through `TestClient` against the real local Postgres and real trained models — including `POST /runs` → poll `GET /runs/jobs/{job_id}` to `"completed"` → confirm the new run appears in `GET /runs`, the actual full round trip a client would do. Separately, the whole stack (below) was verified again through Docker.

## Infrastructure (`Dockerfile`, `frontend/Dockerfile`, `docker-compose.yml`, `.github/workflows/ci.yml`)

Scoped to a single-instance deployment on purpose — no Kubernetes, no Prometheus/Grafana, no enterprise auth; see the roadmap discussion this was planned against for why those would be decoration, not value, at this project's actual scale.

- **`docker-compose.yml`** — three services: `postgres` (official image, named volume, healthcheck), `api` (this repo's `Dockerfile`; `docker-entrypoint.sh` runs `alembic upgrade head` before every start, idempotent), `frontend` (`frontend/Dockerfile`, a Node build stage producing a static bundle served by a second, Node-free nginx stage; `nginx.conf` has the SPA `try_files` fallback so a direct link to e.g. `/runs/<id>` works, not just client-side navigation). `models/`, `data/processed/`, and `reports/` are bind-mounted into the `api` container (not baked into the image), so `docker compose exec api python run_all.py` produces the same files on the host a non-Docker run would.
- **Verified for real against a live Docker daemon** (this sandbox had none; installed `colima` + the Docker CLI to get one) — built both images, brought the full stack up, and by *actually checking `lsof`* caught that an earlier local `uvicorn` process was still bound to port 8000 and silently shadowing the container on `localhost` (colima's port-forward binds `0.0.0.0`, the stale process bound `127.0.0.1` more specifically) — the first "verification" was accidentally hitting the old process, not the container. Killed it, re-verified against the actual container: fresh empty DB, migrations applied automatically, `docker compose exec api python run_all.py && python sync_run_to_db.py` populated it, the nginx-served frontend rendered that data correctly including a direct deep link. Caught and fixed the logging bug described above during this same pass.
- **Known tradeoff, not fixed**: `xgboost`'s Linux/aarch64 wheel pulls in an unused ~350MB `nvidia-nccl-cu12` dependency (CPU-only inference here, no GPU code path) — inherent to that wheel, not something `requirements.txt` alone can avoid without switching xgboost's install source, and not worth the added complexity for this project's scale. The `api` image is correspondingly larger than it needs to be; noted here rather than silently accepted.
- **`.github/workflows/ci.yml`** — two jobs: `backend` (a real Postgres service container, `alembic upgrade head`, `pytest -q` — the DB-dependent tests run for real here, not skipped, since `tests/conftest.py::db_available` only skips when nothing is reachable) and `frontend` (`npm ci && npm run build`, which runs `tsc -b` type-checking before `vite build`). Both fail the workflow on any failure, same bar as running them locally.

## Testing

`tests/` (pytest) covers the pure-function modules — `economics.py`, `calibrate.py`, `counterfactual.py`, `portfolio_opt.py`, `decision_engine.py` (via fake PD/EAD models + an identity calibrator), `stress_test.py`, `src/analytics/*` — plus `run_all.py`'s run-archival helpers (`test_run_archival.py`, which monkeypatches the module's path constants to a `tmp_path` rather than touching real `data/processed/`), the DB layer (`test_db_models.py`, ORM/relationship/constraint behavior against an in-memory SQLite engine for portability — the actual Postgres DDL was verified by hand, see the Database section above; `test_sync_run_to_db.py`, the manifest/DataFrame → ORM-object mapping functions, no DB connection needed), and the API (`test_api_health.py`, `test_api_runs.py`, `test_api_customers.py`, `test_api_jobs.py`, `test_api_auth.py` — via `TestClient`; `test_api_customers.py`'s scoring tests swap `app.state.ml` for the same small fake PD/EAD models `decision_engine`'s own tests use, so they don't need real `models/*.pkl`, while `test_api_runs.py`/the history test in `test_api_customers.py` need a reachable Postgres and skip via `tests/conftest.py::db_available`/`require_db` if there isn't one — the real end-to-end flow, including `POST /runs`'s full background retrain, was verified by hand once, not on every test run, since that's a genuine ~10s retrain). It does not train real models or exercise the full pipeline end-to-end (`test_backtest.py` is the one exception — it does train small real XGBoost models on synthetic data, since that's what it's testing). Regression guards (verified by temporarily reverting the corresponding fix and confirming the suite catches it): `test_counterfactual.py::test_util_mean_uses_only_the_six_period_ratios`, `test_portfolio_opt.py::test_negative_el_uplift_is_not_floored_to_zero`, `test_portfolio_opt.py::test_summary_total_ep_uplift_excludes_rejected_increases`.
